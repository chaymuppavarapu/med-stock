2. PROJECT OBJECTIVE AND BOUNDARIES
============================================================

Create a local, single-user Medicine Stock & Expiry Tracker. It stores a medicine catalogue and separate stock batches, calculates stock totals and expiry status, flags low stock, records quantity changes, and presents a simple dashboard.

IN SCOPE
- Add, search, view and edit medicine records.
- Add and view batches; one medicine may have multiple batches.
- Show total usable stock per medicine and quantity per batch.
- Show expired, near-expiry and low-stock alerts.
- Record stock-in and stock-out changes with a reason.
- Save and reload records using local JSON files.
- Show a simple dashboard and basic inventory/expiry/movement tables.

OUT OF SCOPE — DO NOT IMPLEMENT
- Patient records, prescriptions, dosage or treatment recommendations.
- Billing, point-of-sale, barcode scanning or supplier integrations.
- Automatic purchase orders, notifications, cloud hosting or multi-user access.
- Login/roles, REST APIs, SQL databases, machine learning or external services.
- Regulatory compliance or clinical decision support.

Safety and scope:
This is an educational inventory tracker. It is not a real pharmacy operations or clinical system. Use fictional sample data in demos.

3. REQUIRED DATA
============================================================

Medicine record — required fields:
- medicine_id
- name
- category
- unit
- reorder_level
- is_active

The manufacturer and generic_name fields may be optional. Medicine details are not batch details.

Stock batch — required fields:
- batch_id
- medicine_id
- batch_number
- received_date
- expiry_date
- quantity

Each batch belongs to an existing medicine. Supplier may be optional.

Stock movement — required fields:
- movement_id
- batch_id
- medicine_id
- movement_type
- quantity
- date/time
- reason

Record successful stock changes only. Quantity is a positive change amount.

DATA CONVENTIONS
- Use unique, stable IDs such as MED001, BAT001 and MOV001. Never use a list position as an ID.
- Store dates as YYYY-MM-DD strings in JSON and parse them into date objects for comparisons.
- Quantities and reorder levels must be whole numbers. A received batch must have quantity greater than zero.
- Use one consistent JSON structure across all modules. Lists of dictionaries are sufficient for this project.
- If a medicine has history, prefer marking it inactive over deleting it.

4. CORE BEHAVIOUR AND BUSINESS RULES
============================================================

EXPIRY STATUS

OUT_OF_STOCK:
- Batch quantity is 0.

EXPIRED:
- Quantity is above 0 and expiry date is before today.

EXPIRING_SOON:
- Quantity is above 0 and today <= expiry date <= today + 90 days.

IN_STOCK:
- Quantity is above 0 and expiry date is later than today + 90 days.

Use a single shared function to calculate expiry status everywhere. The 90-day warning window can be a simple constant in Version 1. An expiry date equal to today is not classified as expired under these rules.

STOCK TOTALS AND ALERTS
- Usable stock: sum quantities from batches with quantity above zero and expiry date today or later.
- Low stock: for an active medicine, show an alert when usable stock is less than or equal to its reorder_level.
- Near expiry: show batches within the 90-day window when quantity is above zero.
- Expired stock: show separately and exclude it from usable-stock totals.
- Do not let the UI calculate stock totals independently; call the shared Python logic.

STOCK-IN / STOCK-OUT
- Stock-in increases the selected batch quantity and records a movement reason.
- Stock-out requires a positive quantity and must not exceed the selected batch's available quantity.
- For Version 1, reject stock-out from an expired batch.
- Validate first. If validation fails, do not change quantity and do not create a movement record.
- After a successful change, save the updated batch and movement history.

7. ACCEPTANCE CRITERIA
============================================================

Version 1 is complete only when the following can be demonstrated:

- A user can add, search and edit a medicine.
- A user can add at least two batches for the same medicine with different expiry dates.
- The app shows correct batch status and usable-stock total.
- Expired and near-expiry batches appear in the correct lists.
- Low-stock alert appears when usable stock is at or below the reorder level.
- Valid stock-in/out changes quantity and records a movement with a reason.
- Invalid stock-out leaves both quantity and movement history unchanged.
- Data is still available after closing and restarting the app.
- Missing JSON files are handled by starting with empty collections.
- Malformed JSON produces a clear error and must not be silently overwritten.
- The app runs locally using the README instructions.

REQUIRED EDGE-CASE CHECKS

1. Blank medicine name -> reject and show a helpful message.
2. Batch refers to unknown medicine -> reject batch creation.
3. Negative or invalid quantity -> reject without changing data.
4. Stock-out is greater than available quantity -> reject; no movement is recorded.
5. Invalid date string -> reject and explain the required date format.
6. Batch expired yesterday -> mark expired and exclude from usable stock.
7. Batch expires today -> not expired under the defined rule; apply the 90-day warning rule.
8. JSON file missing on first run -> use an empty collection and create the file on save.
